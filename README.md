# Betalingskenmerk

A small, independent tool that computes the `betalingskenmerk` (payment
reference) for a Dutch Belastingdienst assessment, decision or return —
toeslagen, income tax, VAT (btw), payroll tax (loonheffing) and the other
belastingsoorten — instantly and entirely client-side. Upload the PDF or type
the number; nothing leaves the browser.

**Not affiliated with, endorsed by, or officially sanctioned by the
Belastingdienst.** Independent reimplementation, use at your own risk (see
[Disclaimer](#disclaimer)).

## Why this exists

The Belastingdienst's own [zoekhulp
betalingskenmerk](https://www.belastingdienst.nl/wps/wcm/connect/nl/betalenenontvangen/content/hulpmiddel-zoekhulp-betalingskenmerk)
computes this correctly but needs every field typed in by hand and doesn't read
your PDF for you. Everything it needs is already on the letter you got. This
tool reads the PDF, does the same computation, and gets out of your way.

## What it does

- **Aanslag / beschikking** — upload the PDF (or paste the number) and it finds
  every aanslag-/aangifte-/beschikkingsnummer and computes a betalingskenmerk
  for each. Covers all lettercodes in the official `tabelA`
  (A, B, D, E, F, L, H, N, Y, T, V, W, Z, M).
- **Periodieke btw / loonheffing** — for a periodic VAT or payroll return, enter
  the OB/LH number plus the year and the tijdvak (period); the tijdvak dropdowns
  are driven by the official `tabelB`.
- Shows the Belastingdienst rekeningnummer — from the letter itself if one is
  found on it, otherwise the general account (`NL04 RABO 0200 1122 44`) with a
  caveat to verify against your own letter. See the official
  [uitleg rekeningnummer](https://www.belastingdienst.nl/wps/wcm/connect/nl/betalenenontvangen/content/wat-is-rekeningnummer-belastingdienst).
- A status badge shows whether the underlying algorithm still matches the
  Belastingdienst's own source (see [Drift check](#drift-check)).

## How it works

The zoekhulp does this computation entirely client-side — the logic lives in
[`common/js/iah/betalingskenmerk.js`](https://www.belastingdienst.nl/common/js/iah/betalingskenmerk.js).
The load-bearing pieces were extracted from that source and ported here:

1. **Field mapping.** The dotted number on the letter
   (`1234.56.789.T.25.6.0254`) decomposes into fiscaal nummer (9 digits) +
   lettercode + slotcijfers.
2. **`tabelA`** maps each lettercode to a middelcode rule and the allowed
   slotcijfer length. Most middelcodes are constant; T selects on the last slot
   digit, V on the first two digits of the fiscaal nummer, Y/M/Z on ranges.
3. **Body assembly** differs per lettercode — the 15-digit body is not the same
   field order for every letter. All cases are ported verbatim from the source.
4. **Check digit.** An elfproef-style weighted checksum over the 15-digit body,
   weights `[2,4,8,5,10,9,7,3,6,1,2,4,8,5,10]` applied right-to-left,
   `11 - (sum % 11)` with `10→1` and `11→0`, prepended to the body and grouped
   in fours.
5. **`tabelB`** maps the aangiftefrequentie/tijdvak to a 2-digit tijdvakcode for
   the periodic btw/loonheffing path.

Verified against **all 25 test vectors embedded in the official source** — see
`test/` for the harness. Keep those green if you ever touch the algorithm.

## Drift check

The algorithm could go stale if the Belastingdienst changes it. A live
per-visitor check isn't possible — a cross-origin `fetch()` to
belastingdienst.nl is blocked by CORS. So the check runs out-of-band:

- [`check-drift.mjs`](./check-drift.mjs) re-fetches the official source,
  extracts the elfproef weight array and the full `tabelA`, and diffs them
  against the pinned reference constants.
- [`.github/workflows/check-drift.yml`](.github/workflows/check-drift.yml) runs
  it daily and commits the result to `status.json`.
- The page fetches `status.json` same-origin on load and renders the badge:
  green (`ok`), red (`drift`), or grey (`unknown`).

If the badge turns red, don't trust the tool until someone has re-verified
against the official zoekhulp and updated `REFERENCE` in `check-drift.mjs`.
The per-letter body-assembly code is not diffed (it is code, not data); the
drift check is a tripwire on the tables it depends on.

## Files

| File | Purpose |
|---|---|
| `index.html` | The tool. Single self-contained file, no build step. |
| `check-drift.mjs` | Node script, run in CI, produces `status.json`. |
| `.github/workflows/check-drift.yml` | Schedules the above, daily. |
| `netlify.toml` | Static publish config (serves the repo root). |
| `test/vectors.mjs` | The 25 official test vectors + harness. |
| `status.json` | Generated by the workflow. |

## Deploy

Static site, no build. On Netlify: import this repo, publish directory `.`, no
build command (already set in `netlify.toml`), then attach the custom domain.

## Dependencies

One external dependency, loaded from cdnjs: **pdf.js 3.11.174** — for reading
text out of the uploaded PDF. Nothing else. No analytics, no backend, no
cookies.
